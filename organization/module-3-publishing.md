# 模块3：发布与治理部

## 职责边界

模块3负责回答三个问题：**发到哪**、**发错怎么改**、**整个流程谁在盯着**。

- 输入：模块2验收通过的成片、双语字幕包、模块1的事件归纳与来源证明；
- 输出：多平台发布物、整改台账、流程改进提案、监察报告；
- 不做：选题、下载、转码、刻录、改判素材，也不改写巡检结论与资源登记。

顺序不可颠倒：**先刻录、再备份、最后发布**。成片未进入备份（Release 资产与
filebin 双份）前，不得对外发布；任何一步失败按 P1 处理，不得"先发再补"。

模块3是发布侧的唯一出口。模块1、模块2与巡检体系均不得直接对外发布；
`auto-pipeline`、刻录类工作流不得调用 `deploy-pages`，站点发布只允许 Jekyll
（`pages.yml` / `republish-site.yml`）。

| 司 | 职责 | 不做什么 |
|---|---|---|
| 资源上传司 | 把成片、字幕与说明发布到全球 100 种以上视频/社交/论文平台；维护平台登记与上传台账 | 不改动成片内容，不代替发布后处理司整改 |
| 发布后处理司 | 处理上传后的整改：下架、版权申诉、元数据与字幕更正、补发与更正声明 | 不隐瞒已发生的发布事故，不静默删除 |
| PDCA司 | 制定指标、复盘、流程优化与自迭代升级；维护引擎与平台评分 | 不直接改代码上线，不自授权限 |
| 监察司 | 全流程监督，独立取证，向总控报告；可叫停发布 | 不执行上传与整改，不改动交付物 |

## 资源上传司

### 平台覆盖

平台清单登记在 `publishing/registry.json`，一条平台一条记录，按 `kind` 分为
`video`（视频）、`social`（社交）、`paper`（论文/预印本）三类。

- 硬性下限：**平台总数 ≥ 100**，每类 ≥ 20；当前 127 个（视频 51 / 社交 40 / 论文 36）；
- 记录字段：`id`、`name`、`url`、`kind`、`region`、`api`、`auth`、`status`；
- `api` 只描述已知事实：`official` / `partner` / `none` / `unknown`；
- `status`：`registered`（已登记且具备上传路径）/ `planned`（已登记未接入）/
  `blocked`（明确不可用，须写原因）；
- 校验入口：`python scripts/publishing_registry.py check`。

**登记不等于已接入**：只有存在真实上传适配器、且一次实发成功的平台，才能在
发布台账中记为 `published`。把 `planned` 说成"已覆盖"按登记不实处理。

### 上传规则

1. **来源可追溯**：每个发布物必须带来源视频 ID、原始 URL、事件 ID 与授权说明；
   论文类发布物额外标注是否预印本、是否同行评审。
2. **一平台一记录**：上传结果（平台、账号、时间、返回 ID、URL、状态）写入
   `publishing/ledger/uploads.jsonl`（只追加）。
3. **幂等**：同一成片对同一平台只发一次；重发须有发布后处理司的整改单号。
4. **凭据**：只用仓库 Secrets 或平台 OAuth，不写死、不外借、不共用他人账号，
   不为绕过限额注册随机账号。
5. **平台合规**：遵守各平台服务条款与社区规范；被明确禁止转载的内容不上传。
6. **配比**：White House 原始素材的二次发布须标注"二次剪辑/机器翻译字幕"，
   不得暗示为官方发布。

## 发布后处理司

### 整改范围

上传后发生的以下情形，全部进入整改台账：

| 类型 | 例子 | 处置 |
|---|---|---|
| 下架/封禁 | 平台删除、账号限流 | 记录原因，评估申诉或改投 |
| 版权主张 | Content ID、DMCA | 提交反通知或替换素材，保留证据 |
| 内容错误 | 字幕错译、时间轴错位、事实错误 | 更正或重发，附更正声明 |
| 元数据错误 | 标题、简介、标签、语言标记 | 就地更正并记录 |
| 合规问题 | 隐私、肖像、授权缺失 | 立即下架，报监察司 |

### 时限

| 级别 | 情形 | 首次响应 | 关闭 |
|---|---|---|---|
| P0 | 违法/侵权/隐私风险、错误信息扩散 | 2 小时内下架 | 24 小时内 |
| P1 | 字幕或事实错误、平台封禁 | 24 小时内 | 72 小时内 |
| P2 | 元数据、封面、标签问题 | 72 小时内 | 7 天内 |

超时未关闭自动升级一级，并在周报中单列。

### 规则

1. **不静默删除**：任何下架、重发、替换都要留整改单（原因、证据、操作人、时间）。
2. **更正可见**：事实性错误更正须在简介或置顶评论说明改了什么。
3. **回滚优先**：平台侧无法就地修复时，先下架再重发，不得让错误版本持续在线。
4. **闭环**：整改完成后回写 `publishing/ledger/remediation.jsonl`，并通知 PDCA司。

## PDCA司

### 指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 发布成功率 | 成功上传平台数 / 计划平台数 | ≥ 95% |
| 发布时延 | 备份完成到首个平台可见的中位时长 | ≤ 2 小时 |
| 缺陷逃逸率 | 发布后才发现的内容缺陷 / 全部缺陷 | ≤ 5% |
| 下架率 | 被平台下架或限流的发布物 / 全部发布物 | ≤ 3% |
| 整改关闭率 | 按时关闭的整改单 / 全部整改单 | 100% |
| 引擎命中率 | 采用评分第一引擎的交付占比 | ≥ 80% |

### 循环

1. **Plan**：按月度复盘确定改进项，写目标、口径与验收方式；
2. **Do**：小范围试点（单平台、单引擎），保留对照数据；
3. **Check**：用上表口径比对，偏差超过 20% 视为未达成；
4. **Act**：达成的写入 `organization/` 制度或脚本默认值；未达成的回滚并记录原因。

### 自迭代边界

- 引擎与平台的评分数据在 `docs/engines/data/*.json` 与 `publishing/registry.json`，
  调整须附评测方法与样本量；
- 流程改动先改 `organization/`，涉及根本层级、授权边界或职责原则的，报总控修订
  `DIRECTIVE.md`；
- 自动化只能改配置与登记，不得自行扩大权限、跳过监察或改写巡检结论；
- 每次迭代须能回滚：保留旧配置、旧评分与对照结果。

## 监察司

### 定位

监察司相当于纪委：**独立于被监督对象**，只向总控报告。它不参与上传、整改与
刻录，避免"自己查自己"。

### 监督范围

覆盖模块1、模块2、模块3全流程，重点检查：

1. **合规**：双语是否真的双语、1080p 是否真的 1080p、来源是否可追溯；
2. **顺序**：是否先备份后发布，是否有跳过刻录直接发布的情况；
3. **留痕**：`SOURCES.json`、`FOOTAGE.json`、`BURN.json`、上传与整改台账是否齐全；
4. **权限**：是否有工作流越权调用 `deploy-pages`、是否共用他人账号；
5. **诚信**：是否把 `planned` 平台说成已覆盖、是否隐瞒降级与失败。

### 权限与纪律

- 可调阅全部台账与工作流日志，可要求责任司限期说明；
- 发现 P0 可直接叫停发布并报总控，事后 24 小时内补书面报告；
- 监察司成员不得同时承担上传或整改操作；
- 监察结论只写证据与判定，不代替责任司整改；
- 隐瞒、篡改台账或伪造证据，按最高指示 P0 处置。

### 产出

| 产出 | 频率 | 位置 |
|---|---|---|
| 监察日志 | 每次发布 | `publishing/ledger/supervision.jsonl` |
| 异常单 | 事件驱动 | 同上，`level` 字段分级 |
| 监察报告 | 月度 | `publishing/reports/` |

## 与其他模块的接口

| 上游 | 交付给模块3 | 模块3 回传 |
|---|---|---|
| 模块1 | 事件归纳、来源证明、素材评分 | 发布后的传播数据与更正需求 |
| 模块2 | 成片、双语字幕包、`BURN.json`、备份凭证 | 平台侧字幕/画质问题反馈 |
| 巡检体系 | 工作流健康状态 | 发布链路新增的巡检单元建议 |

模块3发现上游素材或字幕缺陷时，退单给对应模块，不自行改片；确需紧急处理的，
先下架，再按整改单流转。

## 未完成与限制

- 127 个平台中已接入上传适配器的只有 YouTube；Bilibili、X、arXiv 等仍为
  `registered`/`planned`，不得对外声称"已全球分发"；
- `publishing/ledger/` 尚未建立，上传与整改台账的第一条记录待首次实发后写入；
- 监察司目前由 agent 按本制度执行，没有独立的第三方人员；
- 发布后数据回收（播放、下架、版权主张）依赖各平台 API，尚未统一采集；
- PDCA 指标尚无历史基线，首个基线在完成 5 次发布后确定。
